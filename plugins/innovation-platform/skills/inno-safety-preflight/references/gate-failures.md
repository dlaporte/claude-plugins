# When a safety gate fails

Read this when a run of the platform's CI fails one of its gate jobs. The same
gates run on a push to the default branch (`inno-safety-preflight`) and on a
release tag (`inno-ship`), so each failure's cause and fix are here, once. A
release tag's own failures, `Nothing deployed` from
`scaffold-check` (shown as Scaffold check) and those of
`deploy` (shown as Deploy), are `inno-ship`'s table and its
`references/deploy-failures.md`.

A run page, `get_ci_status` and `gh run view` show each job by its name, after
`deploy.yml`'s own job (`platform / Config integrity`), so each row gives the
job's id with that name beside it. A platform before v0.18.16 shows every job
but `app-build` by its id, which each row also gives.

Read the failure yourself and keep the log to yourself (`inno-ship`'s **On
failure: fix quietly, report plainly**, and `inno-safety-preflight` §3 for
what to say). Before any fix that moves, deletes or replaces the user's files,
or edits anything under `.github/workflows/`, ask first, as `inno-ship`'s **On
failure** says. After a fix, push again; on a release tag's run, confirm the
push's gates are green, then cut the next patch tag (`inno-ship`).

| Failing job | Likely cause | Fix |
|---|---|---|
| `config-integrity` (shown as Config integrity) | the repo carries a file the platform injects at build time or one it forbids outright, or `CLAUDE.md` lacks a required header. The failure message names each path; the full list, with the reason for each, is `inno-platform-conventions`' **Files you must not touch** section. A message that the gate "could not fully inspect the app tree" means a committed directory it could not read | **stop and ask; this is not a quiet fix.** Three rules govern how you act on it. **Never move or delete author code unprompted**: files under a root `src/`, and a root `package.json` / `package-lock.json` / `tsconfig.json`, are often the author's real code and manifests in a migrated repo, so show the user every flagged path and, only with their okay, move it under `app/` (for example `app/src/`), updating the Dockerfile `COPY` paths and any imports or build settings that pointed at the old location; delete only what they confirm is not theirs (such as `src/node_modules/`, or a `src/gateway/` an older platform's build left). **Platform-owned files go, once the user okays it** (show them the paths first: a `.env` or `.npmrc` can carry their values, and `inno-ship`'s rule is to ask before any delete): a root `wrangler.jsonc` or any competing wrangler config, a `.wrangler/` directory, a `scaffold/` that outlived `app/.needs-build`, a root-level `.env*` (its values move into app Variables with `set_app_variables`) and any root package-manager config, plus every `.npmrc` at any depth. **A symlink the gate refuses has no policy toggle** (a directory link, a dangling one, or a file link that resolves outside the repository): show the user the link, then replace it with the real directory or file inside the repository, or drop it. If instead `CLAUDE.md`'s required template headers were altered, revert them (the rest of the file is yours). For a directory the gate could not read, fix or remove that path. Everything else under `app/` (an `app/package.json`, an `app/.yarnrc.yml`, an `app/src/`) is yours and fine. |
| `secrets` (shown as Secret scan (gitleaks)), its error titled the same (a failure titled `Gitleaks` is the platform's, below) | gitleaks found a credential committed somewhere in the repository's history, and a file deleted since still counts. It reads every commit on every branch and tag, on every run, a release tag's included, with gitleaks' default rules and the paths they skip (the contract's R8), so an app whose history already holds a secret those rules find fails each push and its next release until it does one of the fixes here. The step log names each finding's commit, file and rule (the secret redacted) and prints its fingerprint | Treat it as real until shown otherwise, and read every finding first: `get_ci_status` shows only the end of the step log, where each finding takes about eleven lines, so about the last two: when the log names more findings than those lines show (gitleaks ends with a `leaks found:` count), read the whole step log on the run link (or `gh run view <run-id> --log-failed` when the user has `gh` signed in) before fixing or waiving any. First **rotate** the secret, since it is exposed whatever happens next, and put the new value in an app Variable (`set_app_variables`), never back in the repo. Then, with the user's okay, either **rewrite the history** to remove it from every branch and tag that holds it, or **record the finding's fingerprint**, as the step log prints it, in a `.gitleaksignore` at the repository root: `<commit>:<file>:<rule>:<line>` waives it in that commit alone, and `<file>:<rule>:<line>` in every commit. A fingerprint stops matching when what it names changes: a rebase or any other history rewrite gives the commit a new id, and a move gives the file a new path, so the finding comes back and has to be recorded again (or, better, removed from the history). **Never** delete the file in a new commit as the fix: the old commit still holds the secret, and the gate stays red. The fingerprint is the only waiver (a committed `.gitleaks.toml` or an inline `gitleaks:allow` comment does nothing); the contract's R8 has the full rule. A failure titled `Gitleaks` (`gitleaks exited <n> without a verdict`, or a runner git older than 2.42 so nothing was scanned) is the platform's, not a finding: change nothing, and never rotate a secret or edit code for it; for `without a verdict`, re-run the workflow once and, if it repeats, ask a platform admin; for the old git, ask a platform admin at once, since the runner's git does not change between attempts |
| `sast` (shown as SAST (semgrep)) | a semgrep OWASP finding anywhere the gate scans, which is the whole repository and not just `app/` (the scope is `inno-platform-conventions`' **Rendering** section; the log names the file). A `secrets: inherit` line in `.github/workflows/deploy.yml` (the finding `yaml.github-actions.security.secrets-inherit`; repos made from older copies of the template carry one) is a blocking finding too, and a real one, not a false positive. A failure titled `Semgrep` (`semgrep exited <n> without a verdict`) or `Semgrep version` is the platform's, not a finding | `inno-platform-conventions` (escaping, SQL); for `secrets: inherit`, tell the user and, with their okay, delete the line (the platform's reusable workflow needs no inherited secrets: it uses only the automatic `GITHUB_TOKEN` and OIDC), keeping the `workflow_dispatch` trigger; for `Semgrep` or `Semgrep version`, change nothing in the code, re-run the workflow once, and if it repeats ask a platform admin |
| `deps` (shown as Dependency audit) | a CVE in `app/requirements.txt` or a production npm dependency (what the audit covers is the contract's R8); or the `Dependency gate` error `could not resolve app/package.json into a lockfile` (a container app's) | bump the pinned dep; for the unresolvable manifest, fix the dependency ranges or commit a `package-lock.json` |
| `dep-age` (shown as Dependency cooldown) | a pinned dep is **too new** for the platform's release-age cooldown (`safety.min_release_age_days`; `get_config app=<name>` gives the value in force and its meaning, and from it how many days you're short by), or `app/package.json` ships with no committed, parseable `app/package-lock.json` so there is nothing to date | **not** a version bump: bumping to the newest release makes it worse. Wait out the cooldown, pin an older vetted version, commit `app/package-lock.json`, or ask a platform admin for an app-scope `safety.min_release_age_days: 0`. Separately from this gate, a function-shaped app that ships `app/package.json` with no committed `app/package-lock.json` fails `app-build` (shown as Build the app Worker) and `deps` (shown as Dependency audit) outright, whatever the cooldown says, in this very run rather than at the tag (the contract's §1.1 **Dependencies** bullet). |
| `container` (shown as Container contract and image scan) | Trivy CVE, a `USER` the non-root gate refuses (the forms it accepts are the contract's R1; `inno-containerize` item 2 applies them), missing `EXPOSE 8080`, or the built image never answered `GET /healthz` with exactly 200 inside the smoke test's budget (R2 gives its clocks); a failure titled `Trivy` (`trivy exited <n> without a verdict`) is the scanner's, not a finding; one titled `Docker build` is the image build | `inno-containerize`; for `Trivy`, re-run the workflow, and if it repeats ask a platform admin; for `Docker build`, fix the Dockerfile or the files it copies |
| `container` (shown as Container contract and image scan) fails with `Accessibility check failed` (only when the app's `safety.a11y.mode` is `enforce`) | the accessibility report found something that blocks in `enforce` mode: an unwaived critical or serious violation, or a landing page `/` (or every page) the app left unscannable. Exactly what blocks, and what only warns, is the `enforce` row of the mode table `get_app_accessibility` serves | read what the report marks as blocking (`inno-safety-preflight` §1c) and fix it, push, confirm the gates are green, then cut the next patch tag. A failing `/` has to render in CI, where there is no stored data, as a real page (an empty state, not an error or a redirect off the app): `app/inno-a11y.json` adds pages that render without stored data, but it never stands in for `/`. A rule that is wrong for this app: name its rule id and have the user ask a platform admin for a time-limited waiver, `safety.ignore.a11y.<rule-id>` with an expiry date as its value |
| `app-build` (shown as Build the app Worker) fails at `Build the app's browser interface` (function-shaped apps; titled `Browser interface entry missing`, `Browser interface build` or `Tailwind build`; on every push) | `Browser interface entry missing`: `app/ui/` has no entry file. `Browser interface build`: an import that does not resolve, or a package the interface imports that sits under `devDependencies`. `Tailwind build`: the stylesheet failed | for a missing entry, add `app/ui/main.tsx` (or `main.ts`, `main.jsx`, `main.js`), or remove `app/ui/`; for a build failure, fix the import or the code the error names (a package the interface imports belongs under `dependencies` in `app/package.json`); for Tailwind, fix the stylesheet (the platform supplies `tailwindcss` itself); then push, confirm `app-build` is green, then tag |
| `app-build` (shown as Build the app Worker) fails with `Missing app/package-lock.json` (function-shaped apps) | `app/package.json` exists but no lockfile is committed (the contract's §1.1 **Dependencies** bullet). This job runs on pushes too, so the failure blocks before any tag exists | run `npm install` inside `app/`, commit `app/package-lock.json`, push, confirm `app-build` is green, then tag |
| `app-build` (shown as Build the app Worker) fails in `npm ci` (titled `Dependency install`), or its `Bundle the app Worker` step reports `Could not resolve "<package>"` with the titled error `Undeclared import`, or reports it with the titled error `devDependency imported at runtime` (function-shaped apps; on pushes as well as tags) | the lockfile no longer matches `app/package.json`, or the code imports a package not declared anywhere (nothing is installed at the repo root), or the code imports at runtime a package declared only under `devDependencies` (`app-build` installs `--omit=dev`, so that tree was never installed) | for an undeclared package: declare it in `app/package.json`, run `npm install` inside `app/`, commit both files, push, confirm `app-build` is green, then cut the next patch tag. For a devDependency: move it as `inno-ship`'s **Moving a devDependency into dependencies** says; then commit `app/package.json` and `app/package-lock.json`, push, confirm `app-build` is green, then cut the next patch tag |
| `app-build` (shown as Build the app Worker) fails with `Symlink escapes the repository` or `Dangling symlink` (function-shaped apps; the step ends `A symlink in your repository points outside it; a link may name only a file inside your repository. Remove it, or point it inside.`); or, from platform v0.18.31, a container app's `container` (shown as Container contract and image scan) fails the same way at its `Reject a symlink that escapes the repository` step, on a push as on a tag | a link in the checkout points outside the repository or nowhere. The check walks the whole checkout but `.git` and the platform's own CI checkout, `node_modules` directories included, which `config-integrity` does not walk: a link an installed package ships, a `file:` dependency that points outside the repository, a link among a `file:` dependency's own dependencies (installed in a `node_modules` beside it), or one in a `node_modules` committed anywhere but the repository root and `app/` (those two are removed before the install). A committed link anywhere else fails `config-integrity` (shown as Config integrity) first. The `container` job's check walks the same checkout before it builds the image, with nothing installed in it, so a committed link out of the repository or to nowhere fails it as well as `config-integrity`, which that job does not wait for. A link may name only a file inside the repository | for a `file:` dependency, bring what it points at inside the repository; for a package that ships such a link, pin a version that ships none, or replace the package; for a committed `node_modules`, remove it from the repository; for any other committed link, replace it with the file it points to, or remove it; each with the user's okay. Push, confirm `app-build` (for a container app, `container`) is green, then cut the next patch tag |
| `app-build` (shown as Build the app Worker) fails with `deploy-bundle failed: the app Worker's bundle is <N> bytes; the platform takes at most 16777216 (16 MiB) before compression` (function-shaped apps) | the built Worker is over the platform's size cap (the contract's §1.1) | drop large imported files, or dependencies the Worker does not use, and keep large data in the app's file storage; push, confirm `app-build` is green, then cut the next patch tag |
| `policy` (shown as Gate policy) fails with `Platform refused this app`, or warns `Gate policy unavailable` | The platform refused this repository's CI, so every gate that needs its answer was skipped and checked nothing: `secrets` (shown as Secret scan (gitleaks)), `sast` (shown as SAST (semgrep)), `deps` (shown as Dependency audit), `dep-age` (shown as Dependency cooldown), `container` (shown as Container contract and image scan) and `app-build` (shown as Build the app Worker). Only `config-integrity` (shown as Config integrity) and `scaffold-check` (shown as Scaffold check) ran; from platform v0.18.31 they wait on the policy job too, so a refusal skips them with the rest. The line says why: most often `app_mismatch` (the repository is registered as another app, which the line names, with the `with: app:` line in `.github/workflows/deploy.yml` to fix) or `repo_unlinked` (the platform GitHub App is no longer installed on the repository). A refusal naming `deploy_denied:workflow` is the author's: `deploy.yml`'s `uses:` line no longer names the instance's pinned workflow. From platform v0.18.26 a refusal can also name `deploys_held` (an ownership move held the app's deploys: its owner keeps or moves its repository), or `app_in_custody` or `owner_inactive` (the app's owner can no longer sign in), each with a sentence that says so. Another refusal that gives no reason (a bare `deploy_denied`, `deploy_denied:repo_owner`, and before platform v0.18.31 `deploy_denied:repo_id` and `deploy_denied:unbound`) says a platform admin can find it. From platform v0.18.31 a repository bound to no app (a fork, a re-created repository) reads the bare one, whose reason the admin finds in the platform Worker's log | `app_mismatch`, `repo_unlinked` and `deploy_denied:workflow` each have a row, with its fix, in `inno-ship`'s `references/deploy-failures.md`: fix it, then push again. So do `deploys_held`, `app_in_custody` and `owner_inactive`, which share one row there: `deploys_held` is the app's owner's to settle (`inno-manage-app`'s **Held deploys: keep or move the repository**), never an admin's, and the other two are an admin's. For a refusal that gives no reason, send the user to a platform admin (`inno-manage-app`'s **Asking a platform admin**). A `Gate policy unavailable` warning is different: the platform gave no usable answer (an outage, not a refusal), so every gate ran on, with no ignores (but the release-age cooldown is off and accessibility only reports), as for a container app; that file has its row too |
