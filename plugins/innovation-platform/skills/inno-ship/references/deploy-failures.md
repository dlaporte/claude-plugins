# Rarer deploy failures and warnings

`inno-ship` loads this when a run shows one of the failures or warnings
below, which its own failure table leaves out because few runs meet them.
They are read and fixed the same way unless the row says otherwise:
diagnose privately, tell the user one plain sentence, fix the root cause,
and cut the next patch tag (a tag is immutable: never force-move one).
Before any fix that moves, deletes or
replaces the user's files, or edits anything under `.github/workflows/`,
show the user the change and ask first. When a row says to offer a support
bundle, `inno-ship`'s **When you're stuck** section says how.

| Failing job | Likely cause | Fix via |
|---|---|---|
| a tag run's `container` job fails at its `Upload SBOM and image id to broker` step with `SBOM upload failed` (container apps), the line carrying `deploy-sbom failed` and the platform's answer | that step records with the platform the image the gates scanned, and a release cannot deploy without that record, so the job fails there and `deploy` does not run: nothing was minted and no deploy started. The line says why, and the cases take different fixes. `sbom_too_large` (`deploy-sbom failed (413)`): the image's software inventory is larger than the platform takes, and the message names the limit and what to change; a re-run builds the same image and fails the same way. A 5xx answer, `deploy-sbom failed: no answer within` its bound, or a network error with no status at all: the platform failed or could not be reached, which is not the app's code. `app_stopped` and `repo_unlinked` (a repo unlinked after the `policy` job passed) each have a row of their own | for `sbom_too_large`, make the image smaller as the message says (fewer installed packages, or a slimmer base image: `inno-containerize`), push, confirm the gates are green, then cut the next patch tag. For `app_stopped`, `inno-ship`'s own `app_stopped` row; for `repo_unlinked`, its row below. For an outage or any other answer, change nothing in the app: re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, stop and offer a support bundle |
| `deploy` stops at `deploy-token failed (409)` naming `image_not_recorded` (container apps), or at `deploy-token failed (502)` naming `upstream_error` and saying the platform could not read the scanned image, or at `deploy-token failed (503)` naming `diagnostics_unavailable` | before it mints anything or starts a deploy, the platform checks that this run's `container` job recorded the image it scanned. `image_not_recorded`: the run recorded none, because its `Upload SBOM and image id to broker` step failed or did not run, as the message says. `upstream_error`: the record is there but could not be read this time. `diagnostics_unavailable`: the platform has no storage to read the record from, which is platform-side. Nothing was minted, no deploy started, and the app is not left deploying | for `image_not_recorded`, read that step in the `container` job: if it failed, follow the `SBOM upload failed` row above; if it passed or did not run, re-run the whole tag run once (`gh run rerun <run-id>`). For `upstream_error`, re-run the deploy job once, as its message says. For `diagnostics_unavailable`, change nothing in the app: tell the user in one plain sentence that the platform could not start this deploy and that their platform admin needs to look at it. If a re-run fails the same way again, stop and offer a support bundle |
| `deploy` fails with `No scanned image recorded` (container apps) | the platform's answer to the deploy job's token request named no scanned image for this run, so the deploy cannot prove which image passed the gates. The platform refuses a run that recorded none before it answers (`image_not_recorded`, above), so no normal run gets here | re-run the whole tag run (`gh run rerun <run-id>`); if it repeats, stop and offer a support bundle |
| `deploy` fails with `Image mismatch`, or finalize refuses `image_mismatch` or `image_not_this_apps` (container apps; the `Finalize deployment` step logs `deploy-complete failed (409)` naming the code) | the image handed to the deploy job is not the one the gates scanned, or (`image_not_this_apps`) the image the deploy pushed is not this app's own repository in the account's registry, pinned by digest; this is never a code bug. Check that `.github/workflows/deploy.yml` still matches `register_app`'s snippet (one `platform` job, nothing that uploads an artifact named `inno-scanned-image`) | show the user how `deploy.yml` differs from the snippet; with their okay restore it, push, and cut the next patch tag (a re-run of the old tag reuses the old workflow file); if `deploy.yml` already matches, re-run the whole tag run; if it repeats, stop and offer a support bundle |
| `deploy` stops at `deploy-token failed (409): {"error":"app_not_ready"}` | the app's provisioning never finished: it has no database or file storage yet, so the platform starts no deploy and records nothing | finish the registration: call `register_app` again with the same arguments (`inno-new-app` §3), then re-run the whole tag run (`gh run rerun <run-id>`) |
| `deploy` stops at `deploy-token failed (409)`, or finalize refuses (`deploy-complete failed (409)`), naming `link_invalid` or `link_source_missing` | the app reads another app's data through a data link that no longer holds, and the message names the link and why (the source is gone, the two apps no longer meet the link rules, or the link has no generation recorded). Nothing went live | not the app's code. Remove the link with `unlink_app_data` (`inno-manage-app`, with the user's okay: the app loses that source's data), have the source's owner fix what the message names, or, for a link with no generation, unlink it and create it again with `link_app_data`, as the message says; then re-run the whole tag run |
| `deploy` stops at `deploy-token failed (409)`, or finalize refuses (`deploy-complete failed (409)`), naming `app_busy`, after the run's own retries (each logged: four attempts over about 50 seconds) | another change to the app, or to an app linked to it, held it for longer than the retries waited: a grant, a link, a change of audience, a variable write, another deploy's finalize | wait a minute, then re-run the whole tag run once; if it repeats, ask the user what else is changing the app right now |
| finalize refuses `host_in_use` or `host_check_failed` (`deploy-complete failed`; an instance whose apps sit at `{name}.{domain}`) | just before attaching the app's address, the platform found a DNS record there that is not the app's own (`host_in_use`), or could not read the zone to check (`host_check_failed`). Nothing was uploaded or attached | not the app's code, and not the user's to fix: tell the user in one plain sentence that the platform could not attach the app's address and that their platform admin needs to look at it. For `host_check_failed` whose message says to try again shortly, re-run the whole tag run once first |
| finalize refuses `deployment_not_completable` (`deploy-complete failed (409)`) | the deployment this run tried to finish is not one the platform can finish. Three cases, told apart by the message. **A message naming a newer deployment**: a newer deploy of the app started after this one, and only that one can go live; this finalize changed nothing. **A message saying the deployment was abandoned or never started**: it was released, after its CI run failed or by the recovery sweep once it went stale, or its start never finished (for one that never started because the app was stopped or unlinked, the message says to start the app first); this finalize changed nothing. **No message**: the deployment is none of this app's, or it stopped being in flight after this run's upload landed, so the new code may already be serving | with a newer deployment: do **not** re-run this release, which would put the older code live over the newer one. Check `app_status` and `get_ci_status` for the newer run; re-run this release only if it should still be the live one, and only once the newer run has ended. Abandoned or never started: do what the message says (`start_app` first when it says the app may be stopped or unlinked), then re-run the whole tag run or cut the next patch tag. With no message: re-run the whole tag run once (`gh run rerun <run-id>`); if it repeats, stop and offer a support bundle |
| finalize refuses `container_rollout_failed` (container apps; the `Finalize deployment` step logs `deploy-complete failed (502)` naming the code) | Cloudflare's rollout of the new image was reverted, replaced, or not complete within 180 seconds. The platform rolls the image out before it uploads the app's host, so no host was uploaded, and the deploy is left uncommitted. A redeploy leaves the address attached from the app's last deploy; an app none of whose deploys has finished has no domain attached yet, so its address serves no app (from platform v0.17.9 it shows a platform page: the one saying the app has not been deployed yet, once the app is released). After a 180 second timeout Cloudflare may still finish the rollout later, so do not promise the user the previous version is what serves. The cause is usually the image itself, a container that does not start or keep running | read the app's container logs (`get_app_logs`, the `container` lines) for why the new container did not come up, fix that, push, confirm the gates are green, then cut the next patch tag. When the logs show nothing of the app's, re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, stop and offer a support bundle |
| finalize refuses `container_policy_unexpected` or `container_namespace_missing` (`deploy-complete failed (502)`), or `platform_key_missing` (`deploy-complete failed (503)`) (container apps) | platform-side, never the app's code, and the deploy did not finish: the app's container application reads back under a scheduling policy the platform does not run (`container_policy_unexpected`), the app's host had no Durable Object namespace after its upload (`container_namespace_missing`, which the namespace's lag behind a new app's first upload can cause), or the platform has no key for the app's host to carry (`platform_key_missing`) | the platform admin's to fix: change nothing in the app, and tell the user in one plain sentence that the platform could not finish this deploy and that their platform admin needs to look at it. For `container_namespace_missing` alone, re-run the whole tag run once first, as its message asks. Then stop and offer a support bundle |
| `policy` fails with `Platform refused this app` naming `app_mismatch`, on a push or a tag run alike; every gate that needs its answer is skipped (only `config-integrity` and `scaffold-check` run), so nothing deploys | the repository is registered as a different app than the one `deploy.yml` names: the platform identifies the app from the signed repository id, and the `with: app:` value (or, with no `with:` block, the name derived from the repo name) disagrees. The line names the app this repository is registered as and the line to set | with the user's okay, set `with: app:` in `.github/workflows/deploy.yml` to the app the line names, or restore `register_app`'s snippet; push, confirm the gates are green, and cut the next patch tag |
| `policy` fails with `Platform refused this app` naming `repo_unlinked`, the line saying the app "is no longer linked to its repository" (the gates that need its answer are skipped); or, for a repo unlinked after the `policy` job passed, a tag run's `container` job fails at its `deploy-sbom failed (403)` line, or `deploy` at a `deploy-token failed (403)` line, naming it | the platform GitHub App was uninstalled from the repo, or the repo was removed from the installation. The broker issues nothing to an unlinked app, and the app itself is stopped and counting down to purge (`list_apps` flags it `[UNLINKED]`) | have the user reinstall the platform GitHub App on the repo, which re-links it; then `start_app` (`inno-manage-app`), push, and cut the next patch tag |
| `policy` fails with `Invalid app name` | the `with: app:` value in `deploy.yml` is not a valid app name | with the user's okay, correct the `with: app:` value (or restore `register_app`'s snippet), push, cut the next patch tag |
| `policy` warns `Gate policy unavailable` | the `policy` job got no usable answer from the platform (none at all, a server error, a brake, a reply it could not read, or a run whose sign-in the platform could not verify): an outage, not a refusal of the app, which fails the job with `Platform refused this app` instead. Every gate then runs on, with no ignores, as for a container app, so a centrally ignored finding fails again and a function-shaped app's `container` job fails, having no Dockerfile to build; a tag run's deploy most often fails too | change nothing in the app. Wait a few minutes, then re-run the whole run once (`gh run rerun <run-id>`); if the warning comes back, tell the user in one plain sentence that the platform could not be reached and that their platform admin needs to look at it |
| a function app's `Hand the bundle to the platform` step fails with `deploy-bundle failed (400): bundle_invalid: <message>` (the `App Worker bundle` error itself reading `deploy-bundle failed (400): bundle_invalid; <message>`), or finalize refuses `bundle_invalid` (`deploy-complete failed (409)`) | the app's built Worker breaks one of the platform's bundle rules, and the message names which: most often a module of a type a function app may not import, a module file name with characters other than letters, digits, `.`, `_`, `-` and `/`, more than 100 modules, or an entry that is not one ES module (`export default { fetch }`, the contract's §1.1) | fix what the message names in the app (what a function app may import is `inno-platform-conventions`' **Node apps** paragraph), push, confirm the gates are green, then cut the next patch tag |
| a function app's `Check the downloaded bundle against app-build's digest` step fails with an `App Worker bundle` error that starts `deploy-bundle failed:` and most often says the downloaded bundle `is not the one app-build built`; also a bundle directory that must hold `worker.form` and nothing else, a `worker.form` that is not a regular file, is empty, is over the size cap or does not start with a multipart boundary line, or `app-build recorded no sha256` | what the deploy job downloaded is not the bundle `app-build` built and pinned by its digest. This step runs right after the download and before the deploy job requests any token, so the platform recorded no deployment and nothing changed. It is never the app's code: most often something beside the `platform` job in `.github/workflows/deploy.yml` uploaded an artifact of its own | change nothing in the app's code. Check that `.github/workflows/deploy.yml` still matches `register_app`'s snippet (nothing beside the `platform` job may upload an artifact) and, with the user's okay, restore it, push, and cut the next patch tag (a re-run of the old tag reuses the old workflow file). If it already matches, re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, stop and offer a support bundle |
| a function app's `Hand the bundle to the platform` step fails with any other `App Worker bundle` error (`deploy-bundle failed (<status>): <code>: ...`, the error itself reading `deploy-bundle failed (<status>): <code>; ...`, naming `bundle_compat_mismatch`, `deployment_not_bundleable`, `not_a_function_app` or `bundle_store_unavailable`, or `deploy-bundle failed: the platform did not answer within 120 s; re-run the job`), or finalize refuses `bundle_missing`, `bundle_mismatch` or `bundle_compat_mismatch` (`deploy-complete failed (409)`) or `bundle_store_unavailable` (`deploy-complete failed (503)`) | the bundle did not reach the platform as the one `app-build` built for this deploy, or the platform could not take it, or did not answer the hand-over within 120 seconds. None of these is about the app's code. `deployment_not_bundleable` most often means a newer deploy of the app started after this one; `bundle_store_unavailable` (503) is platform-side | change nothing in the app. For `deployment_not_bundleable`, check `app_status` and `get_ci_status` for the newer run before re-running anything. For `bundle_store_unavailable`, tell the user in one plain sentence that the platform could not finish this deploy and that their platform admin needs to look at it, then offer a support bundle. Otherwise re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, stop and offer a support bundle |
| finalize fails with `deploy-complete failed (500)`, or the `Finalize deployment` step stops with `deploy-complete failed: no answer within 540 s` | the platform failed in a way it did not expect, or did not answer the finalize within 540 seconds. For a function app it can be the Worker upload failing on the platform's side: Cloudflare refused the platform's own credential (HTTP 401 or 403), found no app namespace (404), rate-limited the platform (429) or failed itself (5xx), or the upload timed out. The step waits longer than the platform's own worst case, so a container app's slow image rollout ends as `container_rollout_failed` (above), not here. None of these is about the app's code. When the failure came at or after the upload, a platform admin finds it in the audit log as `deploy_denied`, its reason the failure's family (`cf_error:404`, say, or `upstream_error` for a timeout) | change nothing in the app. Re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, tell the user in one plain sentence that the platform could not finish this deploy and that their platform admin needs to look at it, then stop and offer a support bundle |
| the deploy job's last step, `Release the app after a failed deploy`, ends in an `App not released` warning | the deploy failed after the platform started it, and the platform did not release the app from it; the warning says why (the platform's answer, no answer in time, a platform that does not have that step's route yet, or no sign-in token because the step that mints it failed). One case: after the `Finalize deployment` step stopped waiting, the finalize still running on the platform held the app. The app stays deploying, so `stop_app`, `restart_app`, `set_app_variables`, `remove_app_variables` and an admin's `purge_app` keep answering `app_deploying`, until a later deploy finishes or the platform's recovery sweep releases it, when the warning says | check `app_status` first: a finalize that was still running may since have finished this deploy. Otherwise fix what failed above it, by its own row, and cut the next patch tag: once that deploy finishes, the app is free. When the user needs one of those tools before then, `inno-manage-app`'s **A deploy whose CI run died** says what holds the app |
