# Rarer deploy failures and warnings

`inno-ship` loads this when a run shows one of the failures or warnings
below, which its own failure table leaves out because few runs meet them.
They are read and fixed the same way unless the row says otherwise:
diagnose privately, tell the user one plain sentence, fix the root cause,
and cut the next patch tag (a tag is immutable: never force-move one).
Before any fix that moves, deletes or
replaces the user's files, or edits anything under `.github/workflows/`,
show the user the change and ask first. When a row says to offer a support
bundle, `inno-ship`'s **When you're stuck** section says how.

| Failing job | Likely cause | Fix via |
|---|---|---|
| `deploy` fails with `No scanned image recorded` (container apps) | the platform has no record of the image this run's `container` job scanned (that job's best-effort SBOM upload failed, or the record could not be read), so the deploy cannot prove which image passed the gates | re-run the whole tag run (`gh run rerun <run-id>`); if it repeats, stop and offer a support bundle |
| `deploy` fails with `Image mismatch`, or finalize refuses `image_mismatch` or `image_not_this_apps` (container apps; the `Finalize deployment` step logs `deploy-complete failed (409)` naming the code) | the image handed to the deploy job is not the one the gates scanned, or (`image_not_this_apps`) the image the deploy pushed is not this app's own repository in the account's registry, pinned by digest; this is never a code bug. Check that `.github/workflows/deploy.yml` still matches `register_app`'s snippet (one `platform` job, nothing that uploads an artifact named `inno-scanned-image`) | show the user how `deploy.yml` differs from the snippet; with their okay restore it, push, and cut the next patch tag (a re-run of the old tag reuses the old workflow file); if `deploy.yml` already matches, re-run the whole tag run; if it repeats, stop and offer a support bundle |
| finalize refuses `container_rollout_failed` (container apps; the `Finalize deployment` step logs `deploy-complete failed (502)` naming the code) | the platform uploaded the app's host, but Cloudflare's rollout of the new image was reverted, replaced, or not complete within 180 seconds. It is never the app's code, and the deploy did not finish: it is left uncommitted, so a later run can finish it | change nothing in the app. Re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, stop and offer a support bundle |
| finalize refuses `container_policy_unexpected` or `container_namespace_missing` (`deploy-complete failed (502)`), or `platform_key_missing` (`deploy-complete failed (503)`) (container apps) | platform-side, never the app's code, and the deploy did not finish: the app's container application reads back under a scheduling policy the platform does not run (`container_policy_unexpected`), the app's host had no Durable Object namespace after its upload (`container_namespace_missing`, which the namespace's lag behind a new app's first upload can cause), or the platform has no key for the app's host to carry (`platform_key_missing`) | the platform admin's to fix: change nothing in the app, and tell the user in one plain sentence that the platform could not finish this deploy and that their platform admin needs to look at it. For `container_namespace_missing` alone, re-run the whole tag run once first, as its message asks. Then stop and offer a support bundle |
| the broker refuses `app_mismatch`: a container app's `container` job logs `deploy-sbom failed (403)` naming `app_mismatch`, the `policy` job warns `Gate policy unavailable`, and a tag run's `deploy` stops at `deploy-token request failed (HTTP 403)` | the repository is registered to a different app than the one `deploy.yml` names: the broker identifies the app from the signed repository id, the `with: app:` value (or, with no `with:` block, the name derived from the repo name) disagrees, and it refuses every request, the policy fetch included. With no policy the gates run all on with no ignores and as a container app, so a function-shaped app shows only the warning and a failed `container` job | with the user's okay, set `with: app:` to the app this repo is registered as (`list_apps` names the repo beside each app), or restore `register_app`'s snippet; push, confirm the gates are green, and cut the next patch tag |
| the broker refuses `repo_unlinked`: the same three signs, the `deploy-sbom failed (403)` line saying the app "is no longer linked to its repository" on a tag run only (the SBOM upload is a deploy-mode call, so on a push the tag-ref check refuses it first and that line reads `deploy_denied:ref`, as it does for every push; `app_mismatch` shows on both) | the platform GitHub App was uninstalled from the repo, or the repo was removed from the installation. The broker issues nothing to an unlinked app, and the app itself is stopped and counting down to purge (`list_apps` flags it `[UNLINKED]`) | have the user reinstall the platform GitHub App on the repo, which re-links it; then `start_app` (`inno-manage-app`), push, and cut the next patch tag |
| `policy` fails with `Invalid app name` | the `with: app:` value in `deploy.yml` is not a valid app name | with the user's okay, correct the `with: app:` value (or restore `register_app`'s snippet), push, cut the next patch tag |
| a function app's `Hand the bundle to the platform` step fails with `deploy-bundle failed (400): bundle_invalid: <message>` (the `App Worker bundle` error), or finalize refuses `bundle_invalid` (`deploy-complete failed (409)`) | the app's built Worker breaks one of the platform's bundle rules, and the message names which: most often a module of a type a function app may not import, a module file name with characters other than letters, digits, `.`, `_`, `-` and `/`, more than 100 modules, or an entry that is not one ES module (`export default { fetch }`, the contract's §1.1) | fix what the message names in the app (what a function app may import is `inno-platform-conventions`' **Node apps** paragraph), push, confirm the gates are green, then cut the next patch tag |
| a function app's `Check the downloaded bundle against app-build's digest` step fails with an `App Worker bundle` error, most often saying the downloaded bundle `is not the one app-build built`; also a bundle directory that must hold `worker.form` and nothing else, a `worker.form` that is not a regular file, is empty, is over the size cap or does not start with a multipart boundary line, or `app-build recorded no sha256` | what the deploy job downloaded is not the bundle `app-build` built and pinned by its digest. This step runs right after the download and before the deploy job requests any token, so the platform recorded no deployment and nothing changed. It is never the app's code: most often something beside the `platform` job in `.github/workflows/deploy.yml` uploaded an artifact of its own | change nothing in the app's code. Check that `.github/workflows/deploy.yml` still matches `register_app`'s snippet (nothing beside the `platform` job may upload an artifact) and, with the user's okay, restore it, push, and cut the next patch tag (a re-run of the old tag reuses the old workflow file). If it already matches, re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, stop and offer a support bundle |
| a function app's `Hand the bundle to the platform` step fails with any other `App Worker bundle` error (`deploy-bundle failed (<status>): <code>: ...` naming `bundle_compat_mismatch`, `deployment_not_bundleable`, `not_a_function_app` or `bundle_store_unavailable`, or `deploy-bundle failed: the platform did not answer within 120 s; re-run the job`), or finalize refuses `bundle_missing`, `bundle_mismatch` or `bundle_compat_mismatch` (`deploy-complete failed (409)`) or `bundle_store_unavailable` (`deploy-complete failed (503)`) | the bundle did not reach the platform as the one `app-build` built for this deploy, or the platform could not take it, or did not answer the hand-over within 120 seconds. None of these is about the app's code. `deployment_not_bundleable` most often means a newer deploy of the app started after this one; `bundle_store_unavailable` (503) is platform-side | change nothing in the app. For `deployment_not_bundleable`, check `app_status` and `get_ci_status` for the newer run before re-running anything. For `bundle_store_unavailable`, tell the user in one plain sentence that the platform could not finish this deploy and that their platform admin needs to look at it, then offer a support bundle. Otherwise re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, stop and offer a support bundle |
| finalize fails with `deploy-complete failed (500)`, or the `Finalize deployment` step stops with `deploy-complete failed: no answer within 180 s` | the platform failed in a way it did not expect, or did not answer the finalize within 180 seconds. For a function app it can be the Worker upload failing on the platform's side: Cloudflare refused the platform's own credential (HTTP 401 or 403), found no app namespace (404), rate-limited the platform (429) or failed itself (5xx), or the upload timed out. For a container app, a slow image rollout, which the platform waits up to 180 seconds for, can outlast the step's wait. None of these is about the app's code. When the failure came at or after the upload, a platform admin finds it in the audit log as `deploy_denied`, its reason the failure's family (`cf_error:404`, say, or `upstream_error` for a timeout) | change nothing in the app. Re-run the whole tag run once (`gh run rerun <run-id>`); if it fails the same way again, tell the user in one plain sentence that the platform could not finish this deploy and that their platform admin needs to look at it, then stop and offer a support bundle |
